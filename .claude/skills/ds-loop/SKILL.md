# 품질 루프

원본 대조(`ds-calibrate`)를 통과한 뒤에 돈다 — 원본을 재현하지 못하는 상태에서 새 요청을 돌리면 빈틈이 재료 문제와 섞인다.

```
시험 요청 → 생성(따로, 지침만 보고) → 검사 · 채점 → 짐작을 칸별 빈틈으로 → 구조로 채우기 → 같은 요청으로 다시 → 전후 비교
```

## 1. 시험 요청 — `quality/requests.yaml`

없으면 디자이너와 만든다. `id` · `request`(사용자가 할 법한 한 줄) · `expect`. 5~10개.
**기준 화면이 있는 요청과 없는 요청을 섞는다** — 앞은 재현, 뒤는 에이전트가 새 화면을 보편 기준으로 지을 수 있는지(일반화)를 본다.
`expect` 는 기계로 볼 수 있게 쓸 수 있다 — `{ screen-type: P-list, require-class: [ds-list], image: K-… }`.

## 2. 채점 — `quality/rubric.yaml`

짜임 · 재료 · 위계 · 상태 · 문구, 항목마다 0 · 1 · 2. **짐작한 것의 수는 점수와 따로 센다**(회차 사이 줄어든 수로 본다).
`expect.screen-type` 이 있으면 decision.md 의 고른 유형과 맞는지, `require-class` 가 있으면 화면에 있는지 먼저 본다.

## 3. 돌린다

요청마다 `ds-generate` 를 생성 세션으로 — 요청끼리 세션을 나눈다. 작업 폴더는 `quality/runs/<날짜>-<회차>/<요청 id>/`.

## 4. 짐작을 구조로 — 이 표대로 채운다

| 짐작 · 감점의 종류 | 채우는 구조 |
|---|---|
| 상태를 어떻게 그릴지(눌림 · 비활성 · 오류) | 그 컴포넌트의 `states` · 상태 처리 문법 |
| 컴포넌트가 없어 data-local · 흉내 | 컴포넌트를 더하거나(새 동작) 골격 · 예시로(늘어놓기) |
| 헷갈리는 둘 중 하나를 골랐다 | 갈림(choices) · 그 컴포넌트의 `avoid` |
| 맞는 화면 유형이 없어 빌렸다 · P-free | 화면 유형(골격부터). P-free 가 같은 일로 두 번 나오면 새 유형 |
| 화면 제목 · 단계 · 고정된 말 | 업무(tasks)의 steps · words |
| 물어야 할 것을 가정했다 | 사실(facts) · 그 사실의 `if-unknown` |
| 간격 · 크기 · 위계를 근거 없이 | 문법(composition)의 수치 · 화면 유형의 regions |
| 분위기 · 밀도를 평균으로 | 그림의 `learn` · 기준 화면 더하기 |
| 어겼는데 검사가 몰랐다 | 규칙 · 문법의 `check` |

**같은 빈틈이 두 요청 이상에서 나오면 먼저.** 한 요청에만 나온 것은 기록만. 값 · 모양을 정해야 하면 디자이너에게(`ds-edit`).

## 5. 다시 돌리고 비교

같은 요청 · 같은 방식으로. 표: `요청 | 점수 전 → 후 | 짐작 전 → 후 | 고친 구조`. 나빠진 요청이 있으면 그 고침이 다른 짜임에 번진 것 — 디자이너에게.

## 6. 남긴다

`quality/log.md` 에 회차마다 — 고친 구조 · 점수 변화 · 남은 빈틈. `npm run ds -- progress loop doing` (끝내는 기준은 디자이너와).
