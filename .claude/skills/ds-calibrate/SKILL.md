# 원본 대조 — 재료부터, 그다음 화면

재료가 원본과 다르면 그것으로 지은 화면은 원본처럼 보일 수 없다. 그래서 **재료 대조 → 화면 대조** 순서이고, 둘 다 통과해야 새 요청 생성(`ds-generate`)이 열린다.
고치는 곳은 늘 **원천**(design/)이다 — 생성된 HTML 을 손보지 않는다. 대조는 **실제 렌더 캡처**로 한다(눈대중 · 기억으로 맞다고 하지 않는다).

## 0. 정답지 모으기

- **컴포넌트 원본 그림:** 피그마의 그 컴포넌트(변형 · 상태가 다 보이는 세트 또는 대표 인스턴스)를 `get_screenshot` 으로 받아 `design/images/` 에.
  `images.yaml` 에 `id: F-<컴포넌트>` · `kind: component` · `applies: ["[[<컴포넌트 ID>]]"]` · `see` · `figma`.
- **기준 화면 원본:** `kind: key-screen` 그림과, 그 화면의 구조를 `get_metadata` 로 받아 파일(`quality/reference/<K-…>.xml`)로 저장한다 — 구조 대조에 쓴다.
- 피그마 MCP 가 없으면 디자이너가 내보낸 PNG 로 하고 그림 항목에 `figma-check: pending`.

## 1. 재료 대조 (calibrate-parts)

컴포넌트 · 조립마다(쓰지 않는 것 — unused — 은 빼고):

```bash
npm run ds -- compare --component <ID>        # 왼쪽 원본(applies 로 이어진 그림) · 오른쪽 우리 렌더(조합표 · 상태) → build/compare/component-<ID>.html · .md
```

1. 두 그림을 **직접 열어 본다**(build/compare/component-<ID>-ours.png 와 원본 그림). 진단표의 줄(변형 · 상태 · 짜임)마다 맞음 · 다름.
2. 다른 곳의 원인 층을 고른다 — 값(색 · 크기 계약) · 작은 컴포넌트(style.css · 변형) · 어휘(이름). 원천을 고친다.
3. 다시 `compare` — 맞을 때까지. 맞으면 spec 에 `calibration: { status: matched, ref: "[[F-…]]", date }`.
4. 피그마에 없는 기준 컴포넌트를 이 시스템에서 쓸 거면, 이 시스템의 값으로 그려진 렌더를 보고 어색한 곳을 고친 뒤 `status: kept`. 안 쓸 거면 `review: { status: unused }`.
5. 원본에 되풀이되는 덩어리(카드 머리 · 요약 줄 · 단계 머리)는 **조립**(`design/composites/<ID>/`, 같은 형식 + `parts`)으로 만들고 같은 방식으로 대조한다.

`npm run status` 의 「재료 대조 n/m」 이 다 차면 다음으로.

## 2. 화면 대조 (calibrate-screens) — 관문

`quality/calibration.yaml` 에 기준 화면마다 한 줄 — `image` · `request`(그 화면을 **말로** 설명한 요청 — 그림의 글을 베끼지 않고, 사용자가 할 법한 말로) · `figma`(저장한 구조 파일).

기준 화면마다 되풀이:

1. **재현 생성** — `ds-generate` 의 1~2 를 따로 도는 생성 세션으로. 작업 폴더 `quality/runs/calibrate-<회차>/<K-…>/`. **생성 세션에게 원본 그림을 주지 않는다**(지침의 그림 목록에 있는 「배울 것」 만) — 그래야 지침만으로 재현되는지 보인다.
2. **대조**

   ```bash
   npm run ds -- compare quality/runs/calibrate-<회차>/<K-…>/<화면>.html --image <K-…> --figma <구조 파일>
   ```

   - 구조 대조(자동): 원본 인스턴스 ↔ 생성 화면의 컴포넌트 — 맞음 % · **빠짐** · 남음 · **대응 없음**(새 컴포넌트 · 조립 후보이거나 spec 의 `figma.name` 을 적을 곳).
   - 눈 대조: 나란히 보기(build/compare/<이름>.html)와 두 PNG 를 직접 열어, 진단표의 층(배치 · 큰 덩어리 · 작은 컴포넌트 · 간격 · 글자 · 색 · 상태 · 문구)마다 0 · 1 · 2.
3. **진단** — 다름마다 원인 층 하나와 고칠 곳. 자주 나오는 짝:

   | 다름 | 원인 층 · 고칠 곳 |
   |---|---|
   | 영역의 자리 · 순서 · 폭이 다름 | 골격(design/layouts/) · 화면 유형의 regions |
   | 원본의 덩어리가 없거나 낱개로 흩어짐 | 조립을 만들고, 골격 · 화면 유형이 그 조립을 가리키게 |
   | 컴포넌트는 맞는데 모양이 다름 | 재료 대조로 돌아간다(그 컴포넌트) |
   | 간격 · 위계가 다름 | 구성 문법(수치) · 플랫폼 문법 |
   | 다른 컴포넌트를 골랐음 | 갈림(choices) · 그 컴포넌트의 use · avoid |
   | 있어야 할 상태 · 문구가 없음 | 화면 유형의 states · 상태 문법 · 문구 문법 · 업무의 words |
   | 원본에만 있는 규칙(예: 주 버튼 자리)이 지켜지지 않음 | 규칙 · 문법에 rule + check |

4. **고치고 다시** — 같은 요청 · 새 생성 세션으로. 회차를 `rounds` 에 적는다(구조 % · 층 점수 · 고친 원천).
5. **통과** — 구조 90% 이상(대응 없음이 남지 않게) · 모든 층 2 → `status: passed`. 원본과 다르게 두기로 한 것은 디자이너에게 묻고 decisions.md 에.

모든 기준 화면이 passed 면 관문이 열린다(`npm run status` 의 calibrate-screens ●). 그다음 새 요청은 `ds-generate` · `ds-loop`.

## 지키는 것

- 이 시스템의 원본에 맞춘다 — 원본이 보편 기준과 다르면 원본이 이긴다(이 시스템의 design/ 안에서). 스타터킷의 기준(kit/)은 고치지 않는다.
- 한 화면만 맞추려고 규칙 · 문법을 그 화면에 꼭 맞게 좁히지 않는다 — 같은 다름이 두 화면 이상에서 나오는지 보고 고친다. 한 화면에만 나오면 그 화면 유형 · 골격에서.
- 끝 보고: 재료 n/m · 화면 n/m, 회차마다 구조 % · 층 점수 변화, 고친 원천, 원본과 다르게 둔 것(누가 정했나).
