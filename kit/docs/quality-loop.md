# 생성 품질을 올리는 흐름

LLM 이 만든 화면의 품질은 그림 솜씨가 아니라 **재료와 기준이 얼마나 빠짐없는가**에서 나온다. 품질 루프는 빠진 곳을 찾아 채우는 반복이다.

```
시험 요청 → 생성 세션(지침만 보고) → 검사 · 채점 → 「짐작한 것」 을 여섯 칸의 빈틈으로 → 채우기 → 같은 요청으로 다시 → 전후 비교
```

## 왜 생성을 따로 시키나

시스템을 짓는 대화는 디자이너의 의도를 이미 안다. 그 대화가 화면을 만들면 지침에 없는 것도 맞게 채워져서 빈틈이 보이지 않는다.
지침 파일만 받은 생성 세션이 만들어야 실제로 제품에서 LLM 이 겪을 빈틈이 드러난다.

## 「짐작한 것」 이 가장 값진 데이터다

생성 세션에게 늘 「지침에 없어서 짐작한 것」 을 빠짐없이 적게 한다. 예시(이전 판의 가계부 예시)에서 첫 생성이 남긴 것:

| 짐작한 것 | 빈틈 | 채우는 법 |
|---|---|---|
| 목록 위 「최근 내역」 같은 구획 제목이 컴포넌트에 없음 | 컴포넌트 | 구획 머리 컴포넌트을 더하거나, 화면 패턴에 「제목 없이 날짜 묶음으로」 라고 적는다 |
| 목록 금액도 빨강인지 모름 | 판단 · 규칙 | 규칙 R-color-meaning 의 범위를 적는다 |
| 「엄지가 닿는 아래」 가 고정 자리인지 본문 끝인지 | 그림 · 컴포넌트 | learn 을 구체적으로 + 아래 고정 자리 컴포넌트 |
| 목록 줄을 div 로 둠 — 누르는 요소여야 하나 | 컴포넌트 | examples.html 을 button · a 로 |

검사는 통과했지만 기준 화면과 달랐던 곳(주 행동 버튼의 자리)이 이 목록에 그대로 있었다. 짐작 목록은 검사가 못 보는 것을 보여 준다.

## 채점

`quality/rubric.yaml` — 짜임 · 재료 · 위계 · 상태 · 문구. 항목마다 0 · 1 · 2. 이 시스템에 맞게 디자이너가 고친다.
짐작한 것의 수는 점수와 따로 센다 — 화면마다 10~20개가 보통이라, 줄어든 수로 본다.
기준 화면이 있는 요청은 나란히 미리보기(`--image`)로 보고 채점한다.

## 어디부터 채우나

- 같은 빈틈이 **두 요청 이상**에서 나오면 먼저.
- 값 · 컴포넌트 · 그림의 빈틈은 결과를 크게 바꾼다. 읽는 법의 일반 원칙은 결과를 잘 바꾸지 않는다 — 원칙보다 **이 제품의 기본값**을 적는다.
- 판단 항목을 늘리기 전에, 그 항목이 컴포넌트으로 그려지는지 본다.

## 첫 시험에서 배운 것 (모바일 HR 앱 · 스타터킷 1판)

- 기준 화면에서만 재료를 뽑으면, 기준 화면 밖의 요청(식당 메뉴 보기)은 가장 가까운 유형을 빌리고 짐작으로 메웠다 — 그래서 2판은 보편 기준(화면 유형 · 사실 · 갈림 · P-free)을 미리 깐다.
- 남은 짐작의 큰 줄기는 화면의 사실(제목 · 흐름 안 위치 · 고정된 말)이었다 — 업무(tasks)의 steps · words 가 그 자리다.
